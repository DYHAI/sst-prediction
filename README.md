# 南海海温预测擂台（SST Prediction）

一个可以上线的海表温度（SST）预测竞赛网站：玩家提交南海 7 个海区、未来 1/3/5 天的
日均海温预测，和三个官方预报产品同台比分，用 NOAA OISST 真实观测结算。

**线上地址：<https://sst.playai.org.cn>**　｜　源码：<https://github.com/DYHAI/sst-prediction>

同一台机器上还托管了总入口页 **<https://www.playai.org.cn>**（含 `playai.org.cn` 顶级域名）：
一个进程、一个端口，靠 Host 头分站——`www`/apex 给入口页，`sst` 给海温擂台。

思路来自 Crosier (2026) 关于 Kalshi 温度预测市场战胜 NBM 的研究——把这套
「人群/市场 vs 官方预报产品阶梯」的方法搬到海洋上，把下注价格换成直接提交数字。

## 一句话说清玩法

| 环节 | 做法 |
|---|---|
| 猜什么 | 南海 7 个海区的**日均海表温度**（°C），分别预测未来 1、3、5 天（经纬度范围见网站「提交预测」页） |
| 什么时候截止 | 目标日往前 h 天的 00:00 UTC。时效越长，必须越早交 |
| 真值 | NOAA OISST v2.1 日平均 SST，按海区 cos(纬度) 加权平均 |
| 跟谁比 | HYCOM ESPC-D-V02、NCEP GFS、NCEP CFSv2，全部按同一规则取数结算 |
| 怎么算分 | 100 ×（0.45×准确度 + 0.20×稳定性 + 0.35×命中率），见 [DESIGN.md](DESIGN.md) |
| 基准是什么 | 同一海区、同一时效下**表现最好的官方产品**的 MAE |
| 怎么交 | 网页手动填；或上传 **CSV / NetCDF / Parquet** 文件；或命令行 / HTTP 接口自动提交 |
| 看什么 | 排行榜、海温场图（真值 / 本站模型 / 误差图）、每条的误差统计 |

## 三种提交方式

```bash
# 1) 网页：提交预测 → 上传整个预报产品（自动解析 + 评测 + 上榜）
# 2) 命令行
python3 -m tools.submit_file --name "我的模型" --file pred.csv
python3 -m tools.submit_file --token <TOKEN> --file pred.nc      # 以后每天自动交

# 3) HTTP 接口（可接进训练脚本）
curl -F name=我的模型 -F token=<TOKEN> -F file=@pred.parquet \
     https://sst.playai.org.cn/api/upload
```

两类文件格式：

```
# 直接给海区值
target_date,horizon,region,value
2026-10-08,3,北部湾,29.85

# 或者给网格场（服务端按同样的 cos(纬度) 规则聚合，自动剔陆地）
time,lat,lon,sst
```

网格场支持 CSV / NetCDF / Parquet，温度写开尔文或摄氏度都能识别。
NetCDF 走 `ncdump` 解析（兼容 NetCDF3/4 与 scale_factor 紧凑编码）；
Parquet 需要先跑一次 `deploy/setup_parquet.sh`。真实海陆掩膜会剔除陆地点，
实测用 GFS 的 GRIB 转成 NetCDF 再提交，解析出来的七个海区值和官方抓取结果**完全一致**。

## 已经跑通的实测结果（2026-10-05）

真值回补 29 天、三个官方产品回补 12 天之后，**共同样本**（所有产品都有数据的 5 天）上的榜单：

| 名次 | 条目 | 类型 | 综合分 | MAE(°C) | RMSE | 偏差 | 命中率 | 样本 |
|---|---|---|---|---|---|---|---|---|
| 1 | HYCOM ESPC-D-V02 | 官方产品 | 68.3 | **0.175** | 0.229 | +0.08 | 96% | 77 |
| 2 | 持续性基线 | 内置对照 | 64.0 | 0.200 | 0.267 | −0.15 | 93% | 84 |
| 3 | NCEP CFSv2 | 官方产品 | 62.7 | 0.194 | 0.230 | +0.07 | 97% | 63 |
| 4 | NCEP GFS | 官方产品 | 18.8 | 0.686 | 0.792 | −0.68 | 38% | 84 |

三个能读出的事实：

1. **格局和论文一致**：最好的单产品（HYCOM，对应论文里的 NBM）领先，
   "什么都不做"的持续性基线紧咬其后，而模式原始输出（GFS）远远落后。
2. **热带海区优势本来就小**：论文里最难赢的是迈阿密（热带、日变化小），
   我们在南海看到的是同一个物理事实——持续性基线能拿到 64 分，
   因为暖池区海温本来就很难报错。
3. **GFS 有接近 −0.7°C 的系统性冷偏差**，这是它分数崩掉的直接原因，
   也说明「偏差」这一项放进综合分是对的。

### 过程中抓到并修掉的两个真问题

这两个坑决定了这套数字能不能信：

**① HYCOM 的 FMRC "best" 聚合会偷跑。**
`best.ncd` 对每个有效时刻只保留*最新*的一次起报。用它取"5 天时效"的预报，
拿到的其实是 1 天时效的值——1/3/5 天拿到的数字完全相同。
必须改成读单次起报数据集 `runs/...RUN_<时刻>`，三个时效才是三次不同的起报。

**② 用瞬时值比日均值，凭空造出 0.3°C 的假偏差。**
OISST 是**日平均**，而一开始产品取的是目标日 00Z 的**瞬时值**。
改成取 00/06/12/18 UTC 四个时次求平均之后：

| | 修复前 | 修复后 |
|---|---|---|
| HYCOM MAE（1 天） | 0.340 | **0.180** |
| HYCOM 偏差（1 天） | −0.327 | **+0.039** |
| GFS MAE（1 天） | 0.817 | **0.486** |

那个 −0.33°C 的"系统性冷偏差"绝大部分是口径错配造出来的假象，不是 HYCOM 的毛病。

**③ ERDDAP 对不存在的日期会"就近吸附"而不是报错。**
请求 2026-10-04（当时数据集只到 10-03）时，ERDDAP 静默返回了 10-03 的数据。
如果不校验返回的日期列，数据库里就会存下一条和前一天一模一样的"真值"。
现在 `app/oisst.py` 会逐行核对日期，对不上直接判失败。

## 本站自己训的模型

训练数据是 **8.75 年（3198 天）** 的 OISST 日网格，
用 `tools/backfill_grid.py` 一次性抓好存成 59 MB 的二进制场，之后训练只要几秒。

**① 线性逆模型（LIM / VAR）** — 把南海按 2° 粗化成 55 个粗格点，减去逐日气候态得到距平，
拟合演化算子 `X(t+τ) = A·X(t) + b`，预报时用截止时刻能拿到的最新观测做初值外推。
纯 Python、零依赖。

**② 梯度提升树（XGBoost / CatBoost / LightGBM）** — 55 维特征：7 个海区在
as_of、−1、−2、−3、−5、−7 天的距平（42 维）＋ 目标日季节谐波与气候态 ＋ 时效与海区 one-hot。

> 这里有个值得一提的坑：**让树直接从零学距平会严重过拟合**——训练 MAE 0.137、
> 验证 0.301，而持续性基线只有 0.18。改成让树只学「相对持续性基线的修正量」之后，
> 验证误差立刻回到 0.19 左右。代码在 `tools/train_ml.py`。

**样本外验证**（`tools/validate_model.py`，训练期截止 2026-05-31，测试 09-06 ~ 10-03）：

| 时效 | 纯持续性 | 阻尼持续性 | 本站 LIM |
|---|---|---|---|
| 1 天 | 0.163 | 0.166 | 0.165 |
| 3 天 | 0.276 | 0.295 | **0.274** |
| 5 天 | 0.372 | 0.390 | **0.370** |

**必须说清楚的结论**：训练数据从 3 年扩到 8.75 年之后，LIM 才从"明显输给持续性"
追到持平、并在 3/5 天上略微胜出；梯度提升树换了几种实现、加了不少特征，
最终也只是和持续性打平。这不是实现问题，而是**热带海温 1–5 天预报本身的天花板**——
暖池区海温变化慢、方差小，持续性极难打败。文献里也是同一个结论。

所有模型都带 **30 天隔离期**：训练数据截止到当天往前 30 天，榜单上每一条成绩
都是真正的样本外预报。

**③ 多源后处理（融合）** — 把 HYCOM / GFS / CFSv2 的预报值 + 持续性当输入，
学一组融合权重，对应论文里「全公开产品最优加权组合」。

> 这里也踩了一个诚实性陷阱：评估用**留一天交叉验证**、出预报用**走前向权重**
> （只拿目标日之前的数据拟合）。如果拿全量数据拟合再回头报历史，会算出
> MAE 0.151 这种虚高成绩（比 HYCOM 的 0.172 还好，是假的），走前向之后落到 0.207。

**④ U-Net 多源空间订正（深度学习，PyTorch + MPS）** — 输入 82×56 的 **10 通道**场：
持续性场 ＋ GFS / HYCOM / CFSv2 三个产品的**预报场**（每个带一个"在不在"标志通道）
＋ 季节与时效，输出订正后的场。

> 训练数据是**真实的历史预报场**：用 AWS 上 NOAA 的公开 GFS 存档 + GRIB 字节索引，
> 每个时次只下 `TMP:surface` 那 600 KB，回补了 **730 天 × 3 时效**（`tools/backfill_gfs.py`，
> 40 MB，约 20 分钟）。
>
> 三个关键设计：① 网络做成**残差式**（输出 = 持续性场 + 修正量），直接从零预测距平会
> 过度阻尼，实测系统性偏冷 0.31°C、比持续性还差；② 训练时按 30% 概率**丢弃产品通道**，
> 否则遇到存档没覆盖的未来日期就会崩；③ **通道要用历史天数把关**——
> HYCOM / CFSv2 的历史场只有上游保留的 9–10 天，训练集里这两个通道 99% 是零，
> 模型根本学不会用；推理时突然喂真值反而像噪声，实测把成绩从 0.24 拉到 0.44。
> 所以设了 90 天门槛：攒够了自动打开，没攒够就老实当成缺测。

## 海洋热浪（Marine Heatwave）

网站新增两个页签：**「海洋热浪」**与**「极端值比拼」**。

判定用 Hobday et al. (2016) 的层级定义：对每个海区、每个日期，
取 **1982–2011 年**气候态在 ±5 天窗口内的 **90 分位**作为阈值；
海温**连续 5 天以上**超阈记为一次事件，间隔 ≤2 天的合并。
强度按 Hobday et al. (2018) 分四级（I 中等 / II 强 / III 严重 / IV 极端）。

为了做这件事，回补了 **1982 年以来的海区日均 SST（15,133 天）**——
气候态基线必须足够长，否则分位数没有意义。回补脚本 `tools/backfill_mhw_baseline.py`
只存 7 个海区的日均值，体积可以忽略；它和本地网格两套口径在重叠期平均只差 **0.0016°C**。

输出的指标：持续天数、平均/峰值强度（°C）、累计强度（°C·天）、事件分级。
每天随抓数任务用 `tools/build_mhw.py` 重算——阈值余量只有零点几度，
真值一更新判定就可能变。

> **口径提醒**：近实时版与最终版 OISST 的逐海区偏差实测只有 **±0.08°C**（20 天平均），
> 远小于阈值余量（约 0.5–1.5°C），所以没有做版本订正，但这条记在页面上。
> 另外，固定基准期（1982–2011）在变暖背景下会让近年热浪天数系统性偏多，
> 这是定义本身的特性，不是数据问题。

## 极端值上的模型比拼

把每个条目的成绩**按目标日是不是热浪日拆开**，再单独检验热浪识别能力：

| 指标 | 含义 |
|---|---|
| 热浪日 MAE / 正常日 MAE | 同一个模型在两类日子上的误差 |
| 劣化幅度 | 热浪日 MAE 相对正常日涨了多少 |
| POD（命中率） | 真热浪日里被预报出来的比例 |
| FAR（空报率） | 预报的热浪里其实不是的比例 |

> 有个发现值得单说：官方产品目前只有最近约 10 天的结算样本，
> 而**这 10 天恰好整段处在一次南海全域热浪里**——所以 HYCOM / CFSv2 / GFS
> 在"正常日"那一列是空的。等历史攒起来才能真正对比。

### 热浪专项榜（按识别能力排序）

这张榜**不看温度报得多准**，只看能不能提前认出热浪。

不能直接按 POD 排：本窗口热浪日占一半左右，**一律报"是"就能拿 POD=100%**。
所以主排序用两个对随机猜测公平的评分（极端事件检验的标准量）：

| 指标 | 定义 | 随机猜测 | 完美 |
|---|---|---|---|
| **ETS** 公平威胁评分 | (命中 − 随机命中) ÷ (命中+空报+漏报 − 随机命中) | 0 | 1 |
| **TSS** 真实技巧统计量 | POD − 空报率 | 0 | 1 |

专项分 = 100 × (0.6×ETS + 0.4×TSS)。入榜要求热浪日与非热浪日**各 ≥ 15 条**——
否则空报率会被算成 0、评分假性满分（官方产品现在就是这个情况）。

实测结果（近一年窗口）：

| 名次 | 条目 | 专项分 | ETS | TSS | POD | FAR |
|---|---|---|---|---|---|---|
| 1 | 本站 U-Net 订正 | **73.1** | 0.684 | 0.802 | 82% | 3.1% |
| 2 | 持续性基线 | 68.4 | 0.627 | 0.768 | 80% | 3.7% |
| 3 | 本站 LIM | 64.0 | 0.585 | 0.724 | 75% | 3.8% |
| 4 | 本站 ML · CatBoost | 63.8 | 0.581 | 0.724 | 76% | 6.0% |
| 5 | 本站 ML · LightGBM | 63.6 | 0.578 | 0.724 | 78% | 8.3% |
| 6 | 本站 ML · XGBoost | 59.9 | 0.539 | 0.689 | 74% | 7.9% |

> **这张榜验证了一件事**：U-Net 在主榜（按 MAE）排第 9、几乎是自研模型里最差的，
> 但在热浪专项榜**排第 1**。认不认得出热浪、和温度报得准不准，确实是两种能力。

## 2023–2026 长期回测（1–10 天时效）

上面那些榜单都受限于"官方产品只有两周历史"。为了做长时段对比，
用 AWS 公开存档把 **GFS 的历史预报场回补到 1–10 天时效、2023-01-01 起**
（`tools/backfill_gfs_leads.py`，每个场只下 `TMP:surface` 那 600 KB，
用 eccodes 的 Python 绑定直接取数组而不是解析百万行文本）。

回测设计刻意做得简单、可复现：

```
训练期 2023-01-01 ~ 2024-12-31
测试期 2025-01-01 ~ 2026-09-30   ← 所有模型都没见过
时效   1, 2, 3, ... 10 天
```

参与对比：气候态 / 持续性 / 阻尼持续性 / **NCEP GFS** / 本站 LIM / 本站 XGBoost / 本站 U-Net。
脚本 `tools/backtest_long.py`，输出 `data/backtest_long.json`，网站「长期回测」页读取。

> **为什么只有一个官方产品**：HYCOM 上游 FMRC 只保留约 9 次起报、年归档是原始 restart
> 二进制（`data.hycom.org/.../archm/` 的 `.a/.b`）；CFSv2 的 NOMADS 只留约 10 天、
> NCEI 的业务归档路径已 404。这两个产品拿不到长历史，只能靠每日抓数累积。

### 结果（MAE，°C）

| 时效 | 气候态 | 持续性 | 阻尼持续性 | **NCEP GFS** | 本站 LIM | 本站 XGBoost | **本站 U-Net** |
|---|---|---|---|---|---|---|---|
| 1 天 | 0.640 | 0.100 | **0.098** | 0.844 | 0.098 | 0.119 | 0.132 |
| 3 天 | 0.640 | 0.240 | 0.227 | 0.871 | 0.228 | 0.264 | **0.220** |
| 5 天 | 0.640 | 0.337 | 0.307 | 0.898 | 0.310 | 0.356 | **0.290** |
| 10 天 | 0.640 | 0.482 | 0.393 | 0.937 | 0.412 | 0.462 | **0.393** |
| **平均** | 0.640 | 0.329 | 0.290 | 0.895 | 0.297 | 0.341 | **0.288** |

三个能读出来的结论：

1. **1–2 天：简单方法赢。** 阻尼持续性 0.098，U-Net 0.132。海温一天之内几乎不变，
   任何模型都很难超过"把昨天的观测搬过来再稍微收缩一下"。
2. **3 天起：U-Net 反超，并且一直领先到 10 天**（5 天领先 5.4%，10 天打平）。
   这时持续性的信息已经衰减，网络学到的空间结构开始有用。
3. **GFS 的原始海表温度场很差**（平均 0.895，比气候态还差）。
   它是大气模式的表面温度，在近岸浅水区偏差很大——这也解释了为什么它一直在榜尾。

### 热浪日 vs 正常日（跨全部时效汇总）

| 模型 | 热浪日 MAE | 正常日 MAE | 劣化 |
|---|---|---|---|
| 气候态 | 1.205 | 0.433 | +178% |
| 持续性 | 0.336 | 0.327 | +3% |
| 阻尼持续性 | 0.313 | 0.282 | +11% |
| NCEP GFS | 1.253 | 0.763 | +64% |
| 本站 LIM | 0.277 | 0.304 | **−9%** |
| 本站 XGBoost | 0.289 | 0.360 | **−20%** |
| 本站 U-Net | **0.267** | 0.295 | **−10%** |

**一个反直觉但合理的结果**：传统方法和 GFS 在热浪日都变差（+3% ~ +178%），
而三个数据驱动模型在热浪日**反而更准**（−9% ~ −20%）。
原因不难理解——热浪期间海温距平大且持续，信号强、噪声占比低，
模型学到的距平演化正好派上用场；反过来在"平常日子"里距平很小、
局地噪声主导，谁都不好报。

## 各模型的独立验证结果

| 模型 | 验证方式 | 结果 |
|---|---|---|
| LIM | 样本外（训练截止 2026-05-31） | 5 天 0.370 vs 持续性 0.372 |
| 多源后处理 | 留一天交叉验证 | 0.187 vs HYCOM 0.180（**还没赢**，样本只有 7 天） |
| U-Net（多源场） | 样本外 588 条 | **0.239 vs 持续性 0.262 vs GFS 原始 0.588** |

网站「方法与文献」页有「各模型的独立验证结果」卡片，实时读这三个脚本产出的 JSON，
另外还有一张「多源场库积累情况」表，能看到 HYCOM / CFSv2 的通道还差多少天才能打开。
每个数字都能用仓库里的命令复现。

**关于 U-Net 的诚实说明**：它在 525 条样本的样本外测试里比持续性好约 7%，
但**打不过 HYCOM**；在榜单那个只有 4 天的共同样本上甚至排到持续性后面——
样本太小 + 那几天刚好是 U-Net 不擅长的时段。这正是榜单存在的意义：
谁都可以把自己的模型接进来，用同一把尺子量。

## 快速开始

```bash
cd /Users/dingding/Desktop/Program/SST_Prediction

# 1. 抓真值与官方产品（首次建议回补一个月）
python3 -m tools.ingest_truth --days 30
python3 -m tools.ingest_products --days-back 12 --days-ahead 8

# 2. 起服务
SST_PORT=8770 python3 -m app.server
# 打开 http://127.0.0.1:8770
```

依赖：Python 3 标准库 + `eccodes`（`brew install eccodes`，只用于解 GRIB2）。
Web 服务本身零第三方依赖。

## 改动后自检

```bash
python3 -m tools.build_mhw          # 热浪事件
node tools/render_check.js          # 每个页签的渲染（需要服务在 8770 跑着）
```

`render_check.js` 用最小 DOM 桩把每个页签的渲染函数真跑一遍，顺带检查
"页签按钮 ↔ 区块 id"是否一一对应。**这个是踩过坑之后加的**：
加新页签时忘了同步"隐藏/显示区块"的那个列表，点新页签会把所有区块都藏起来，
表现成一片空白——而接口是好的、HTML 也是好的，静态检查完全看不出来。

## 部署

见 [deploy/README.md](deploy/README.md)。要点：

1. **launchd 常驻**：`deploy/com.playai.sst.plist`（服务）、`deploy/com.playai.sst.ingest.plist`（每天两次抓数）
2. **cloudflared 隧道**：`sst.playai.org.cn` → `127.0.0.1:8770`
3. ⚠️ macOS 会阻止 launchd 进程访问 `~/Desktop`，需要给 `/opt/homebrew/bin/python3`
   开「完全磁盘访问权限」，否则服务起不来。这一步必须在系统设置里手动点。
